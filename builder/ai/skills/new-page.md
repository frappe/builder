# New page or full redesign

## Before you build
- New page or major redesign: you need two things before you build, what the page is for (brand/name and what makes it distinctive) and its design direction (its overall visual character). The default design direction is the site's own. Unless the user asked for a specific style or a deliberately different look, first check whether the site already has designed pages (query_records 'Builder Page', excluding the open one; published and recently modified first). If it does, read_page one to three of them (the home page first), derive the system (the exact fonts, palette handles or hexes, shared chrome components, section rhythm), build to match it, and skip the layout-direction question (only this page's content questions remain). If those pages visibly disagree with each other, don't guess: ask one present_ui question, which page's look to follow (the pages as options), with a fresh direction as the last option. read_page each candidate before describing it, and build from what you read, not from that description. Only an empty site, or an explicit wish for a new look, gets the creative design flow below.
  - A page that grows out of existing content (a detail page for a section, another case study, a page per product): find its parent or siblings yourself (query_records 'Builder Page' with a like filter on route or title), read_page the closest and inherit its design, chrome and links. A detail page lives under its collection as a dynamic route ('partners/<partner_id>'), whose params reach the page data script as frappe.form_dict.<param>. Read the site's routes before choosing one; when the user insists on one that collides with an existing page, say so and offer the nearest free one.
  - What to ask: one card, unless the request already says what the site is for, what it should hold and how it should feel; then build with no card. A choice the user hands you ('pick the look yourself', 'build it now') is made, not asked: skip its step. Read what the user pointed you at first (their current site with read_url, a listing), so the card offers their real content instead of asking for it. Ask it as one present_ui card, a multi-step form submitted at the end, with every question you already know you need. When the answers raise new ones (three case studies, so what each one should show), ask those in a follow-up card before building. Its steps, skipping any the request answers: (1) what it's for and who it's for, with the name when there is none (input); (2) what it holds: one multi choices of the sections or pages that fit this kind of site, prefilled from what you read (a personal site: writing, talks, projects, about, resume, contact); (3) layout direction, only when the request names no feel or vibe and doesn't leave the look to you (choices, each tile carrying its palette); (4) the specifics that make it theirs; then one closing {kind:'actions', buttons:[{label:'Build it'}]}. A redesign answers (1) and (2) from the page itself: its card asks only what's left. Never ask about anything the request states or the user already answered, and never invent a brand name or positioning.
  - Layout direction options are structurally different from one another: each implies a different page layout, not just a different colour scheme. Give every option a one-line description that sells the difference, and its palette as `colors` (four or five hexes you designed for this brand's world): the tiles are the only place a palette is chosen, so the user picks between whole, coherent looks, never between hexes. Think like an art director raiding print and place, not a template gallery: a menu-as-poster, a broadsheet front page, a zine spread, a vintage produce label, a ticket stub, a shop window at night, a field guide, a Swiss timetable. Name each option like a concept ('The Morning Paper', 'Poster Wall', 'The Ledger'), never an adjective pair like 'Modern Minimalist'. Each maps to one of the generator's layout systems (editorial-grid, split-screen, bento, poster-brutalist, dense-utility, single-object stage, zine-collage), and its description names its signature move (one concrete device: oversized price-list numerals, vertical spine text, a full-height photo gutter, ruled ledger lines, a stamped seal) and its imagery treatment ("photos run duotone in the awning red", "one huge knockout product shot, nothing else"). At least one option should be a surprise the user wouldn't think to ask for but that fits the brand. Avoid three options that are one layout described three ways, and the light-minimal / dark-bold / warm-friendly trio.
  - Typography is your call, never a question: pick the pairing yourself and name it in the brief. Fix the brand's type personality in a phrase ('precise technical field guide', 'loud retro poster', 'quiet stationery shop'), then find faces that embody it; a bakery, a law firm and a synth label never share fonts. {{font_draw}} Never the faces generated pages all share, in any of their cuts: {{stock_faces}}. If your pick is the first that came to mind, or would fit a totally different brand as well, pick again.
  - Options are starting points, not a menu. "The third one, but with an elegant purple palette" is a normal answer: take that option's layout, apply the tweak, and don't re-ask.
  - A named vibe ("minimal", "playful", "calm, sunlit, tactile") answers how the page should feel: design to it, with no direction step. When a card is still needed for something else and you offer directions anyway, make them structurally distinct takes on that mood, not three recolours.
  - Never ask for colours: most users can't judge colour harmony, and a palette picked hex by hex clashes. You design it, and the direction tiles carry it. Derive it from something specific to this brand (its material, its street, its product, its photos), never from its category. A warm near-white ground of any name (cream, paper, bone, ivory, sand, linen, beige) with a terracotta or orange accent and sage beside it is the stock generated look: use it only when the user asks for it or their brand already has it. Choose the ground on purpose: pure white, near-black, or a colour with real saturation that you'd name. Colours the user volunteers (brand hexes, a logo) are law in the roles they named; with an existing brand (their site, a logo), derive from it. You may add derived shades. If their colours clash, honour them and say so in one frank sentence.
  - The specifics step makes the page theirs; its lead-in is simply something like "A few specifics for the page:". Optional inputs adapted to the business: signature products or offerings by name, a one-line origin or founder story, the location. Don't ask or offer how the page should move: pages are built still unless the user raises movement. Every answer surfaces in the built page's copy, verbatim or nearly so: a named croissant, a real founding year, the actual neighbourhood.
  - A page that must match the rest of an existing site never gets a fresh design direction. Skip the layout step and read the site's real system first: read_page the reference page the user named (or the home page; get_document('Website Settings') names it), plus the theme variables (query_records 'Builder Token') and the existing components, and stop there. When the user named the page or site, that page alone is the reference: every read_page this turn feeds the generator as reference geometry, a site grown through experiments can hold several clashing systems under one brand, and an extra read is how a contact page comes back wearing the wrong page's palette. The first page you read is treated as the primary reference downstream, so read the page to match first. Then write the brief from what you read (the reference's exact fonts and palette, its $token handles or hexes, its section rhythm) and embed the existing header and footer components (div use(<id>)) instead of rebuilding them. Matching aligns the system around the page's content; it doesn't erase an identity the page already has: a theme, copy and imagery direction from earlier turns survive "make it match" unless the user says to drop them. Matching also carries motion: read_page returned the reference's CSS/JS page scripts, and a still page beside moving siblings reads broken, so name the class hooks its scripts need in the brief (per the class-contract rule), then after generate_page returns, attach the reference's scripts with attach_page_script (the doc stays shared, so the site's motion lives in one place); copy a trimmed set_page_script only when a script also does work unrelated to this page. A site whose pages move is the user having opted into movement; the no-animation default governs fresh builds, not matching. Ask only this page's content details.
  - An attached image of a page design (a mock, a screenshot, "use this design", "like this") is the approved design direction: skip the layout-direction step, derive the palette, type personality and layout system from the image, and ask only what the image can't answer (name, copy specifics). The message carrying the image names its saved url; the brief repeats that exact url on its own line as REFERENCE IMAGE: <url>, which is what puts the image in front of the generation step. An attached photo of a real subject (their product, shopfront, portrait) is content to place (HERO IMAGE: <url>), never a design direction.
  - If one image defines the page (a hero photo, a product shot, a logo) and the request doesn't give it, add a photo step to the same card: search_images first, then a choices step of 3-4 photo options (option.image = each result's thumb) and an upload atom as the "or your own" option. Skip it when imagery is decorative.
- There is no plan or approval step: once you have the essentials (from the brief plus any cards you needed), build. A plan card that restates what the user told you and asks them to click "Build it" is friction; the user watches the page build live and can Revert. Carry the full working brief straight into generate_page's `brief`: the layout system name, the signature move, the imagery treatment, exact headlines and key copy in 'single quotes', per-section layout, the palette (the chosen tile's, with any hexes the user gave in their roles), fonts, every personal detail gathered, and any REFERENCE IMAGE: / HERO IMAGE: url lines.
- A change the user asks for before the build ("make it a centered showcase", "darker palette") goes into the brief, not back to them as a question. After the build, further changes are ordinary edits.

## Building a page: one turn, minimum rounds
The user watches every tool call as live progress, so batch independent calls into the same round. Skip steps the brief doesn't need; never reorder across rounds.
1. Foundation, one round: mint the design system as tokens, all set_design_token calls together (pass explicit `id`s so you know every $<id> handle upfront; reuse existing tokens where they fit): the palette (type Color, e.g. 'auel-ink') and both font families (type Font, e.g. 'auel-font-heading', 'auel-font-body', value is the bare family name). Colour and type are the only tokens, so one token edit rethemes the site; spacing, sizes, gaps and radii are literal values on the block (padding:96px 24px), where they stay editable on the canvas. Also in this round: search_images for the photos the brief needs, the data setup when the page is data-driven (read_skill('forms-and-data') in this round; its data script and DocType tools follow, and create_doctype and seed_sample_data are confirm-gated and pause the turn), and the page's identity via set_page_settings: page_title = the brand ('Stillpoint'), route = a clean brand slug ('stillpoint'), meta_description = one line. A page built for a brand never keeps a placeholder title ('Untitled', an old test name) or a default 'pages/<id>' route, unless the user set those themselves.
2. Layout, one round: generate_page builds the page the user has open. The brief carries the layout system name and signature move, the imagery treatment, the brand name and positioning, the section list with real copy intent, the palette and fonts as the exact $<id> token handles (plus their values; font-family uses the font token handles), the spacing rhythm as literal values, every personal detail gathered (these appear in the copy), the exact image URLs as marker lines (HERO IMAGE: <url>, REFERENCE IMAGE: <url>, plus any section photos), and any data keys to bind repeaters to.
   No animation unless the user asked for it. A page ships still: no scroll reveals or fade-ups, no @keyframes, no parallax, marquee, count-ups, typewriters, custom cursors or hero interactions, and no page script to drive any of them. Subtle CSS hover transitions are not animation and stay. The design has to hold up standing still. The one standing opt-in is a match build: when this page matches a reference whose scripts move (see the match rule above), carry that motion by attaching the reference's scripts.
   When the user does ask for movement (now or later), build it on a class contract: decide the hooks (hero → 'auel-hero', each reveal target → 'auel-reveal') and name them in the brief so the layout carries them.
3. Scripts, after the page exists: write them once generate_page has returned. Its result hands back the real page and flags any hook the layout didn't carry, so a script written then targets classes you can see; one written earlier guesses at a page that doesn't exist yet, and a selector that misses fails silently. The CSS script (classes and @keyframes) and the JavaScript script (observers and listeners, never a <style> tag built from JS) go in one round together.
4. Verify: preview_page after every generate_page build; fix breakage, AI tells and the failures its rubric lists with surgical edit_page edits, never by regenerating. If those fixes changed layout, preview once more to see them land. Then finish with your summary.
One-shot builds (the user skipped the design flow): choose a distinctive direction yourself, pick the layout system and signature move that fit the brand and say which you chose; a centered template look only when the user asked for conservative.
