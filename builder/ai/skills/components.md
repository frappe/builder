# Components

- Shared chrome everywhere: (a nav link, the footer copy, a new menu item, a declared prop), call edit_component on the component itself: it saves the definition and syncs every page that embeds it. A patch on an instance's inner ref changes only this page's instance, so it is never the tool for a site-wide change, and neither are page-by-page edits.
- Shared chrome is a contract, not just a component: on many sites it is component blocks, plus companion page scripts on every page that embeds it (a sidebar's hover-expand, a nav's toggle), plus the classes wiring the two. read_page shows a reference page's components with their root layout styles and its attached scripts. When you embed a component a reference uses: (1) attach the same companion scripts with identical content, because a from-memory reimplementation drifts just enough to break; (2) trust the component's own root styles, since it sizes itself, and wrapping it in width/margin constraints is how a sidebar collapses or vanishes. If the layout still fights you after that, the missing piece is almost always one of its scripts, not another wrapper.
- How component instances work: an instance renders the component's own blocks with their default content, and those internal blocks appear in your tree under the instance, each with of() naming the component-internal block it mirrors (join of() against the component's default content to pick the right ref). Patching such a ref overrides only this page's instance (text, styles, attributes), and that is how shared chrome comes to belong to the page: a breadcrumb names this page's trail (never left reading 'Home'), a nav's active state points here, a part that doesn't apply gets display: none. Components can also declare props (read_page and get_document show them with defaults): when a prop exists for what you want to change (an active tab, a title, a variant), set it with props(name=value) on the instance root; that is the component's intended customization surface, cleaner than overriding its children. A component may also carry its own server data script (component_data_script on the Builder Component doc: it receives the instance's props and fills the component.* bindings); read it before assuming what an instance renders. read_page lists each embedded component's default content, its props, and the overrides the reference's own instance applies (including hidden ones, where the reference suppresses the shared chrome and builds its own variant); mirror that pattern on your page. A page that embeds chrome and leaves its defaults showing is unfinished.
- Component client scripts: a component's blocks can carry their own behaviour and styling (the `js |` / `css |` bodies under a block, set by an edit_page patch on an instance root or a block inside one; rejected on plain page blocks). The js is the body of a function run once per rendered instance, with `this` = that instance's DOM element and (component_data, props) as arguments: plain statements, no wrapper, no DOMContentLoaded, reach inside with this.querySelector, never document-wide selectors. The css is auto-scoped to the block's subtree, so plain selectors are safe. Select by class hooks you set, never by structure: the rendered HTML is not your block tree (bound and repeater text renders as plain text-block divs, not the p/h tags you authored), so querySelector('p'), sibling walks and tag-based closest() silently miss; give the blocks you need classes (.faq-answer) and select exactly those. Scripts and first-time prop declarations you set on an instance mirror into the component definition automatically, so every future embed gets them. When you build a component (the user asked for one, or you extract one), finishing means making it self-contained: after extract_component, move both the behaviour js and its css into the instance's js | and css |, then neutralize any page script you wrote for it during the build (update_script with a '// moved into the component' stub); leaving both alive double-fires the handlers, and a component that needs this page's scripts is not reusable. Its content must travel too: inside a component, write list items out as real blocks, not as a repeater bound to a page-data key, since that key exists only on this page. Text that mirrors a prop (a title, a count, a starting value) is bound to it, bind(text=props.<name>), never hardcoded: the binding makes the canvas reflect prop edits instantly, while the client script only animates or updates it at runtime. A static preview cannot run your script, so never tell the user the interaction "works": say what you wired and that a click in the preview will confirm it. `props` is a plain object of the instance's resolved prop values (overrides merged over declaration defaults): read props.active_tab directly. `component_data` is only what the component's server data script put under component.component_data (other component.* keys feed bindings, not the client script), so a data script that wants its results client-side mirrors them there (component.component_data = {"items": items}). Behaviour that belongs to a component (a sidebar's hover-expand, a nav's toggle, a tab switcher) lives here: it ships with every embed and receives the instance's props; the copy-the-companion-page-script ritual exists only for older components built without one. Everything else (page-wide interaction, motion, styling hooks on ordinary blocks) stays in page scripts, where the user can see and manage it.
