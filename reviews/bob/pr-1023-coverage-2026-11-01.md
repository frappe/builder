## Original defects that still need attention

These are gaps in previously discussed findings, separate from ambitious new features.

1. **Valid but empty generation can still replace a draft.** Strict parsing fixes malformed YAML and stream truncation, but `el: div` with empty `c` still reaches `persist_page` and a database write. An isolated probe of the current function returned a root with zero children and one mocked `set_value` call. There is no semantic candidate-completeness gate. See [page_writer.py](/home/t3run/builder/builder/ai/page_writer.py:552), runtime F3.
2. **Permission coverage remains incomplete for references and shared effects.** Direct `get_document` now checks document/field permissions, and run admission/start checks the target page. However, `read_page` still loads another page through raw lookups, `preview_page` gets it without a document read check, and component definition mirroring writes directly without component authorization. Shared script/token paths still use `ignore_permissions=True`. This is a source-confirmed gap, not a claim that a live restricted record was accessed. See [query.py](/home/t3run/builder/builder/ai/agent/tools/query.py:195), [preview.py](/home/t3run/builder/builder/ai/agent/tools/preview.py:121), [tree.py](/home/t3run/builder/builder/ai/agent/tree.py:245), capability F02/F03.
3. **Free-text card qualifications can remain hidden.** The actual `cardAnswers` function reduces `Poster, but change this: keep all prices in euros` to `Poster, but change this`; the panel hides the original user bubble when any answer is inferred. The backend retains the text, but the visible record loses the qualification. Reproduced offline. See [cardAnswers.ts](/home/t3run/builder/frontend/src/components/ai/cardAnswers.ts:51) and [BuilderAIChatPanel.vue](/home/t3run/builder/frontend/src/components/BuilderAIChatPanel.vue:585), session F16.
4. **Beginner suggestions still insert fictional complete briefs.** The pizza/photographer/yoga suggestions supply invented identities and details and invite immediate building. They are editable prefills, not automatic sends, but the requested personal-intent onboarding was not implemented. See [BuilderAIChatPanel.vue](/home/t3run/builder/frontend/src/components/BuilderAIChatPanel.vue:594), P-UX1.
5. **Older chats remain unreachable through normal history selection.** The endpoint defaults to 20, caps at 50, and has no cursor; the picker requests the default. Active-chat deletion is now rejected and failures are surfaced, but pagination/search and a deletion tombstone protocol are missing. See [api.py](/home/t3run/builder/builder/ai/api.py:583) and [AIChatController.ts](/home/t3run/builder/frontend/src/components/AIChatController.ts:673), session F13.
6. **Batched tool calls still reorder writes and discard work after a terminal card.** The loop applies client operations first, then runs remaining handlers sequentially, returning at the first terminal result. There is no durable deferred batch or safe parallel-read scheduler. Mutation counting is still tool-name-based: even a non-failing, empty image search can count as a mutation. See [loop.py](/home/t3run/builder/builder/ai/agent/loop.py:1297), runtime F11.
7. **Page locks do not supply revision-aware mutation or undo.** The new run protocol has no expected page revision/effect receipt contract. Atomic Revert fixes history loss but does not provide conflict-aware undo of newer independent edits, shared components/tokens, schema, records, plugins or all page settings. Pending confirmations prevent duplicate application, but a crash in `action_applying` still needs reconciliation. See [api.py](/home/t3run/builder/builder/ai/api.py:149), [api.py Revert](/home/t3run/builder/builder/ai/api.py:282), [snapshots.py](/home/t3run/builder/builder/ai/snapshots.py).
8. **Component and plugin lifecycle findings remain.** Component extraction still strips placement without preserving it as instance overrides; direct definition mirroring bypasses the normal version/sync path. Plugins are still activated before meaningful functional validation, and replacement/unload is not transactional. The final transaction fix prevents destroyed-savepoint errors; it does not stage/undo plugin installation. ## Flow: review versus implementation

The [Flow review](flow-session-review.md) and [proposed server contract](flow-server-contract.md) answer the worker question: Flow's daemon awaits actual asynchronous model I/O outside a Frappe web/RQ worker. Short submission requests and tool callbacks still consume workers while executing. A human pause persists state and ends the running operation; restart reconstructs journal state, not an interrupted provider stream or Python stack.

The PR adopts some prerequisite ideas: durable admission/run identity, an outbox, cancellation and recovery. It does **not** adopt the Flow daemon, async provider execution, durable event cursor/replay, transactional tool receipts, expected-revision callback checks or a complete continuation record.

Bob remains synchronous RQ. `builder_ai_queue` can isolate it on a provisioned AI queue; otherwise it uses `default`. Isolation protects general jobs only when deployed appropriately; the AI worker itself remains occupied. Moving only the coordinator, while page generation stays a long synchronous callback, would not finish the migration.

The reviewed `frappe-flow==0.1.20` requires Python >=3.14 and LiteLLM 1.103.2, while Builder declares Python >=3.10 and pins LiteLLM 1.95.1. The review recommends an explicit service/dependency decision rather than an implicit baseline upgrade. Flow was pinned at `9562f406e2c246ffe80e51d27768fac50e4a17e5`; this audit did not re-review a newer Flow revision.

## Recommended order to finish the experiment

1. **Close the remaining correctness holes first:** valid-empty generation, target-specific reference/shared permissions, typed card answers/display, history access, component lifecycle and explicit shared-effect/revision handling. Keep plugin staging/disposal as its own focused change.
2. **Build one complete personalized design path:** personal-intent starters → short editable brief → two or three actual Builder-native hero/section variants → selected real assets → chosen variant becomes the draft → responsive verification. Replace mandatory design formulas with relevant optional recipes. This directly tests the user's principal product goal.
3. **Complete media and verification:** one licensed paid acquisition path with receipts/budgets, transformations/mobile crops, selective generated art, visual URL inspection and deterministic browser/accessibility/form checks. Add a small tested motion library only with these checks.
4. **Move model orchestration to an async service:** use the Flow boundary or a compatible equivalent, with durable journal/replay, idempotent mutation receipts and permission/revision checks. Include page generation and research, not only the chat coordinator.
5. **Run the acceptance experiment:** trace each matrix ID to a fixture/evaluation; establish a baseline, repeated generation samples and blind design comparisons; measure cost/time/corrections to acceptance. Expand to multi-page projects after single-page invariants hold.

The appropriate description of #1023 is **“reliability and guided-design foundation.”** Neither “all review findings resolved” nor “MotionSites-level generation implemented and validated” is supported by the current code or evidence.
