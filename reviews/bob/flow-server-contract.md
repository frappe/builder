# Flow server contract for Bob — interim architecture finding

Reviewed `frappe/flow` `main` at **9562f406e2c246ffe80e51d27768fac50e4a17e5** (clone `/tmp/bob-flow-review`). No Flow `AGENTS.md` exists in the checked-out tree. Builder instructions were read; no Builder files changed.

**The user's inference is substantially correct: Flow's long LLM loop runs in a dedicated async daemon, not a regular Frappe RQ job.** Frappe web requests briefly submit work to it; ordinary tool callbacks still occupy web workers for their execution, and explicitly background tools occupy RQ workers. It is not a general guarantee that nothing blocks workers.

1. **Separate process.** `flow/daemon/lifecycle.py:189–211` supports a supervised foreground service; `225–237` can launch a detached process. `252–275` constructs `flow serve --uds <socket> --data-dir ... --profile deployed`. The Frappe app declares a Pilot process in `pyproject.toml:43–45`. [Lifecycle source](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/flow/daemon/lifecycle.py#L189-L275).
2. **Short synchronous submission, then async execution.** Frappe's `DaemonClient` uses synchronous HTTP over a Unix socket, with site header and bearer authentication (`flow/daemon/client.py:26–53`). `run()` posts without `wait=true` (`89–92`). The daemon's async route starts `session.run()` (`server/routes/sessions.py:322–326`); `_start_operation()` assigns an `asyncio.create_task()` to the session (`session/session.py:584–596`). `_finish()` waits for completion only if explicitly requested (`server/routes/sessions.py:501–506`). Thus the web request does not await the whole model turn. [Client](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/flow/daemon/client.py#L26-L99), [task creation](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/session/session.py#L584-L596), [response](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/server/routes/sessions.py#L501-L506).
3. **Actual async provider I/O.** `LiteLLMModel.run()` is an async event iterator; the streaming adapter awaits `litellm.acompletion()` and consumes it through cancellation-aware async iteration (`model/litellm.py:169–189`). This is not a synchronous stream hidden inside `async def`. [Provider source](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/model/litellm.py#L137-L189).
4. **Waiting for the user settles the task.** Gated calls produce durable `ApprovalRequired` plus `RunEnded(reason="paused")`, and the loop returns (`agent/loop.py:329–337`). The session derives `paused` from the pending approval after its task finishes (`session/session.py:260–265`). `resume(answers, approval_seq=...)` validates the exact pending batch under the session operation lock and starts a new operation (`345–368`). No RQ worker or live model request waits for the human. Bob's design-question cards should use the same persisted continuation pattern even though they are not security approvals. [Pause](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/agent/loop.py#L329-L337), [resume](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/session/session.py#L345-L368).
5. **Durable history, not arbitrary stack checkpoints.** A typed append-only JSONL log stores run boundaries, messages, tool results, usage, approval batches and compactions. Reload reconstructs the transcript. A paused approval survives restart; an in-flight run does **not** resume a Python stack or a provider stream. Reload closes unfinished tool calls and marks an open run interrupted/error (`session/session.py:237–255`). Tool effects completed just before a crash still need independent reconciliation. [Recovery](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/session/session.py#L237-L255), [log](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/session/log.py#L31-L82).
6. **Tool callbacks are the remaining occupancy boundary.** The daemon uses `httpx.AsyncClient` to call Frappe; a callback can return `{pending:true, timeout:N}`, then deliver a result using a random `result_token`. Ordinary tools run in the callback's web request as the session owner. Background tools enqueue on `queue="long"`, commit their effect, and then deliver the result. The daemon waits asynchronously on an in-memory future. These futures do not survive daemon restart. The `tool_waiting` preflight avoids some stale jobs but is not an atomic cancellation/side-effect fence. [Async callback contract](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/agent/client_tools.py#L26-L67), [Frappe execution](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/flow/daemon/callback.py#L41-L72), [RQ path](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/flow/daemon/callback.py#L128-L169).

## Concrete Bob recommendation

Move **all model orchestration** to a supervised Bob runtime service: coordinator, page-generation model stream, summarizer, research model calls and title generation. Keep Frappe responsible for authenticated admission, page/document permissions, brief/assets, canonical mutations and short database transactions. Moving only the coordinator while making `generate_page` a long Frappe callback would still tie workers up for the expensive part.

Use the following boundary:

- `run(page_id, session_id, request_id, prompt, model, ...)` validates, atomically creates a durable queued Bob run and its user message, and returns `{session_id, run_id, status:"queued"}`. A durable outbox dispatches to the runtime after commit, with idempotent `run_id`; a short relay/reconciliation task is acceptable in RQ. A naked after-commit HTTP call is insufficient: its failure after commit must not lose accepted work. Keep new-session creation idempotent too.
- The runtime claims an operation, records `running`, and executes async provider I/O. Do not call synchronous `AgentRunner.run()` from the daemon's event loop or share Frappe request globals among async sessions. Explicitly bound concurrent model calls and expensive tools. Start with one runtime owner per session; multiple daemon processes need partitioned ownership or distributed leases/fencing, not just `asyncio.Lock`.
- Every durable event carries `{session_id, run_id, seq, type, payload}`. The runtime owns the execution journal; Frappe's chat/run rows are projections, with a synced cursor. Keep canonical page writes and their `(run_id, tool_call_id)` effect receipt in the **same Frappe database transaction**. Repeated delivery returns the stored outcome. Avoid two independently writable transcript histories.
- A mutation callback authenticates service/site, resolves the persisted run owner, rechecks permission, cancellation and expected page revision, and records accepted operations plus a receipt. Make synchronous callbacks short. Long image/network jobs run in the daemon or a separately provisioned tool queue; normal site queues must not host model-stream waits.
- `awaiting_input` persists `{card_id, revision, typed_fields, partial_answers, continuation}` and returns from the operation. Resume names this exact continuation; stale/double submissions are rejected or return the first result. No parked RQ job waits on a card. Resume should preserve selected model, original objective and approved brief independently of rolling chat history.
- `cancel(session_id, run_id)` durably transitions that exact run, including queued work, to cancellation requested/cancelled. The runtime checks before the first provider request and each new mutation. Closing a remote HTTP await does not roll back a callback already executing; effect receipts and revision checks must account for partial outcomes.
- Reconnect reads snapshot + cursor and subscribes/replays missing durable events. Publish committed events after persistence; partial text/YAML is replaceable preview state. On runtime restart mark active runs interrupted and reconcile tool receipts before explicit continuation. Paused cards restore directly from durable state. Do not promise transparent resumption of a half-finished external write.

## Dependency decision

The reusable standalone package is **`frappe-flow==0.1.20`**, import namespace `flow_harness`, MIT licensed. It supplies `SessionStore`, `SessionConfig`, `Session.run/resume/abort/compact/events/event_snapshot`, typed events, provider adapters and an HTTP daemon. The Frappe `flow` app is a separate integration layer. `Agent` is an in-process convenience wrapper, **not** what frees a Frappe/RQ worker: iterating `Agent.run()` inside that worker still occupies it.

At this commit the harness requires **Python >=3.14 and LiteLLM 1.103.2**; Builder declares Python >=3.10 and pins LiteLLM 1.95.1. Do not add the package to Builder's current dependency set as a drop-in fix. Either use a separately provisioned Python 3.14 Flow service with a Bob-specific client/tool/event adapter (validate its HTTP/runtime gaps), or port the small event/session contracts into a separately supervised Bob runtime compatible with Builder's supported environments. The standalone harness is a much smaller candidate than installing the complete Frappe Flow app, but neither is a zero-cost integration.

Flow itself does not yet supply Bob's required idempotent run admission: `RunRequest` accepts only `message`/`attachments` and returns a status; active submissions can become in-memory steering. Add Bob's stable `request_id`/`run_id`, durable queue and cancellation identity at this boundary instead of claiming Flow already provides them. [Request schema](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/server/routes/sessions.py#L47-L51), [package constraints](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/pyproject.toml#L1-L22).
