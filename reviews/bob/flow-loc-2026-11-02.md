# How much Bob code could Flow replace?

This is a migration estimate, not an implemented deletion or a proposal to replace Builder's website tools with generic coding tools. Compared Builder `5ea6e3c98781c6b2c5a8650d36d1e1b429980af8` with current `frappe/flow` main, `9562f406e2c246ffe80e51d27768fac50e4a17e5` (verified through `git ls-remote`). Flow is still `frappe-flow==0.1.20`, the revision covered by the [earlier architecture review](flow-session-review.md). That review's description of Bob predates its current async runtime and must not be used as the present baseline.

**Plan around 1,000 fewer maintained source lines with Flow sessions and Bob's current UI, or around 2,000 with substantial Flow UI reuse.** The defensible planning ranges are approximately **400–1,900** and **850–3,000 net physical lines**, respectively, after new adapters. These correspond to roughly **2–8%** and **4–12%** of Bob's 24,203 physical production lines. They are estimates of the final migration, not a measured patch. Flow's largest benefit is sharing maintenance of a difficult runtime, rather than eliminating most of Bob.

The savings estimates below use **physical lines, including comments and blanks**. The separately measured code-only baseline is 18,935; do not divide these savings by that smaller number. Without implementing the adapters, converting their estimated length into an exact code-only saving would imply precision we do not have.

## Migration choices and net savings

All three choices retain Builder's tools and product behavior. They are alternatives, not additive stages. The first also requires a compatible Python environment or separate daemon.

| Final architecture | Old physical lines removed | New adapter physical lines | Net reduction | Planning midpoint |
| --- | ---: | ---: | ---: | ---: |
| Flow model/execution engine; keep Bob session storage and UI | 1,050–1,300 | 530–850 | 200–770 | ~500 |
| Flow canonical sessions/events; keep Bob's current chat UI | 2,559–3,270 | 1,360–2,200 | 359–1,910 | ~1,100 |
| Flow canonical sessions/events and shared chat components; retain Bob-specific cards/canvas | 3,499–4,669 | 1,680–2,650 | 849–2,989 | ~1,900 |

Bounds use conservative independent extremes: minimum deletion minus maximum adapter size, and maximum deletion minus minimum adapter size. Midpoints are planning aids, not statistical predictions. The exact-looking totals come from adding the scoped ranges below; use the rounded headline when budgeting work.

These are **steady-state Bob-owned production** estimates. They exclude tests, schema JSON, one-time historical-session import/deployment scripts and new Flow upstream implementation. Those still require work. Maintaining both old and new engines, keeping the old RQ implementation, vendoring Flow, or needing a permanent private Flow fork can erase the savings. The initial migration PR will probably add code before it removes it. Existing regression coverage should move to the integration boundary, not be deleted to improve the LOC metric.

### Where the estimates come from

Two independent source reviews covered execution and session/frontend boundaries; the parent review measured the whole inventory and the additional Codex transport opportunity. The following slices are disjoint for deletion accounting:

| Slice | Gross removal, physical lines | New production glue, physical lines |
| --- | ---: | ---: |
| Execution only: `runtime`, `workflow`, `scheduling`, `agent/loop`, `budgets`, `llm` | 750–950 | 450–700 |
| Same execution files when Flow also owns sessions | 1,100–1,400 | 700–1,100 |
| Session/API and frontend lifecycle, retaining current chat components | 1,159–1,520 | 580–950 |
| Session/API and frontend, adopting Flow chat components instead | 2,099–2,919 | 900–1,400 |
| Additional Codex wire transport replacement, all choices | 300–350 | 80–150 |

The execution adapter covers typed model events, tool execution, nested generation/research, dynamic schemas, terminal controls and request budgets. Its full-session increment covers daemon execution context, callback fields and consumer migration. The session/API adapter covers durable dispatch acknowledgement, page-linked access/listing, approval/effect references and coordinated Revert. The frontend adapter covers transport/store hooks, rendering and retained canvas integration. These are conservative allowances; a common implementation may share some mapping code. Deleting a function and moving its domain logic to an adapter earns no saving.

The **Codex increment** is additional to `llm.py` and `runtime.py`. `codex.py` has 303 physical / 270 code lines in the transport functions listed below. Replacing their SSE/chunk/payload implementation with Flow's native provider, plus nearby scaffolding, supports the 300–350 gross estimate. Allow another 80–150 physical lines for provider-native message/identity and model-limit adaptation beyond the execution review's existing credential allowance. Keep model catalog behavior, site/provider credential storage and hosted device-code sign-in. Do not count the entire 570-line module or all provider settings as deletable.

## What is worth delegating to Flow

Flow's [`Agent`](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/agent/agent.py#L23) wraps its durable `Session`. Its loop, provider adapters, cancellation-aware retries, event transcript, pause/resume, context compaction and stream client overlap Bob's generic infrastructure. The [shared Vue package](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/ui/core/src/index.js) exports a generic `DaemonClient`, store/reducer and individual chat components. The Frappe host separately implements a [168-line relay stream](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/frontend/src/api/stream.js) and [311-line Frappe client](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/frontend/src/api/client.js). Those are not already a drop-in exported Builder client; copying them would add locally maintained lines.

Meaningful savings require Flow to own the model loop and, in the larger migration, the authoritative session/event history. Running the existing `AgentRunner` as a Flow tool leaves most of the same implementation in place. Keeping two authoritative event journals also creates synchronization work that offsets deletions.

Bob already awaits coordinator, generation, research and OAuth network I/O outside Frappe web/RQ workers in its async mode. Flow would replace the custom implementation of that boundary. Its ordinary Frappe tools still occupy a callback request, and background tools still use an RQ worker. Page-generation model waits must remain in the daemon rather than moving into a long synchronous callback.

## Responsibilities that remain in Bob

- Native block/YAML conversion, working-tree edits, components and script attachment.
- Page ownership, current-run checks, revision conflicts, savepoints, accepted-operation receipts, protected content and real Revert across page/shared effects. Flow conversation rewind does not restore Builder documents or reverse purchases.
- Design briefs, chosen facts/assets, real desktop and section previews, exact variant application, refinement, multipage plans and verification.
- Image providers, licenses/acquisition, generated artwork, private uploaded assets, attribution and media budgets.
- Builder's card forms, optional preview/tweak UI, asset choices, editable next-step chips, canvas following and affected-item UI.
- The current site's provider permissions, credential storage and device-code sign-in until an equivalent integration exists.

The existing `agent/tools` modules alone contain **4,118 code lines**. Their domain logic does not disappear with Flow. The directly embedded `Tool(parameters=...)` dictionaries account for **1,032** of those lines. Flow's typed decorators could reduce some schema boilerplate, but they require replacement annotations/models and the same descriptions. Moving text into docstrings is not a genuine reduction in responsibility; the main estimate gives no automatic credit for deleting all these schemas.

## Integration costs and constraints

1. **Python/Frappe/dependency baseline.** Builder declares Python 3.10+, Frappe 15.121.3–17 and `litellm==1.95.1`. Flow's harness requires Python 3.14+ and `litellm==1.103.2`; its Frappe app requires Python 3.14 and Frappe 16–17. This prevents simply adding it to every currently supported Builder bench. A separately provisioned Flow daemon can isolate Python dependencies, at the cost of RPC/deployment integration. The test bench being Python 3.14 does not remove Builder's published compatibility contract.
2. **Dynamic tool loading.** Bob enables specialist schemas/policies during a turn. Flow assembles the tool schema list at the start of its loop. Preserving Bob's small initial context needs a supported refresh/extension point or an adapter; sending all tools from the start changes the token-efficiency behavior.
3. **Tool result identity and rich data.** Local Flow tools carry `ToolContext.tool_call_id`, `ToolResult.details` and attachments. Its remote callback payload omits the call ID, and the current remote dispatch returns only `content`/`is_error`. Bob needs stable effect IDs, accepted operations, preview/card metadata and attachments across this boundary. See [`call_client`](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/agent/client_tools.py#L26) and [`_dispatch`](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/agent/loop.py#L648). These need upstream support or explicitly maintained glue.
4. **Admission and ownership.** Flow's running-session messages become in-memory steering. Its request API does not supply Bob's durable submission-id/outbox guarantee. Keep the deduplication and page/run fences; choose a single daemon owner or partition ownership deliberately. Its JSONL journal's process-local lock is not a cross-worker database transaction.
5. **Credentials.** Flow has a Codex OAuth/model implementation, but its standalone credential store is a user-global file. Bob stores provider credentials in Frappe and supports hosted device-code login. Transport reuse is realistic; deleting all provider configuration and sign-in code would change supported behavior.
6. **Different budget semantics.** Flow counts observed fresh input/output usage, excluding cache reads; Bob reserves estimated input plus output ceilings before calls. The new million-token setting cannot simply be copied between them while claiming equivalent behavior. Keep a conservative admission policy or explicitly change its contract.
7. **Compaction improvement and cost.** Flow can generate a durable model-written summary, preserve recent messages and retry an overflow once. Bob currently abbreviates/trims deterministically. Flow's richer compaction costs additional model calls; briefs and accepted decisions still need durable structured storage outside a generated summary.
8. **Frontend distribution and behavior.** Flow links `@flow/ui-core` from its own source workspace; the public npm registry returned 404 for that package during this investigation. Reuse needs a pinned external source/package boundary. Copying its implementation into Builder is not counted as deletion. Its bundled suggested replies send on tap, while Bob's requested behavior fills an editable composer. Visual-card and canvas behavior still need custom integration.
9. **Terminal and batch behavior.** Bob ends on the first successful terminal card/reply and defers subsequent tool calls. Flow's [`ends_run` check](https://github.com/frappe/flow/blob/9562f406e2c246ffe80e51d27768fac50e4a17e5/harness/src/flow_harness/agent/loop.py#L770) happens after the batch and requires all calls to be successful ending tools. A mixed card/write batch is therefore not equivalent. Bob also rejects an entire response with malformed tool JSON, while Flow can execute valid calls alongside an invalid one. Both need an explicit dispatch policy before migration.
10. **Revert across stores.** Flow conversation rewind changes its transcript, not Builder documents. A Flow JSONL append and a Builder DB transaction are not one atomic operation. Preserve the existing guarded page/effect restoration and add a recoverable protocol for the transcript branch/projection; a naive restore-then-rewind can again lose history or restore only half the state.

## Recommendation and proof boundary

Use Flow for the shared model/runtime responsibility if we are prepared to contribute the missing extension points upstream. Preserve Bob's design and Builder integration layer. Start with a small provider/loop integration experiment; only move canonical session ownership once its admission, effect and Revert contracts work. Keep the present Bob UI during that experiment. Moving the UI primarily to reduce LOC is a larger product decision with uncertain value.

Before committing to the full migration, demonstrate these cases using mocked providers and real isolated Frappe transactions:

1. Same-turn `load_tools` makes the newly enabled tool and policy visible to the next model call without sending every schema initially.
2. A terminal card followed by a mutation in the same response does not execute that later mutation; malformed batches preserve the chosen rejection policy.
3. Slow coordinator, generation and research waits consume no web/RQ worker; cancellation preserves the last valid page and reconnect restores the preview.
4. Lost admission responses, duplicate delivery, queued cancellation, daemon restart and two browser tabs preserve submission identity and page/run ownership.
5. Tool call IDs and rich result details survive the daemon/Frappe boundary, with only committed accepted operations reaching the editor.
6. Revert fails or recovers consistently across page DB state, effects and the Flow transcript; it never silently deletes history after a failed restore.
7. Site-scoped provider credentials refresh safely; retries, compaction and nested calls honor the budget and missing-usage contract.
8. Durable typed answers, real raster preview selection/tweaks, attachments and editable next-step chips survive refresh.

Then measure the actual removed and added production code. If the integration needs a large private fork or a second canonical journal, keep the present runtime until Flow exposes the needed boundary. Better automatic summaries and provider-native reasoning continuity may justify adoption even with modest LOC savings, but reduced LOC alone does not establish better design quality or lower token spend.

This investigation changed documentation only. No migration, application/runtime changes, service restarts, provider calls or live tests were performed.

## Counting method

The inventory includes tracked `.py`, `.ts`, `.vue`, `.js` and `.cjs` files under `builder/ai`, `frontend/src/components/ai` and `builder/builder/doctype/builder_ai_*`, plus `AIChatController`, `BuilderAIChatPanel`, `AIDebugPanel` and `AIAffectedItems`. Filenames starting `test_` or containing `.test.` go in the test bucket. Builder AI DocType `.json` files go in the schema bucket.

Reproduce against the pinned Builder commit, using the CSV's `production` paths as the file manifest:

```sh
curl -fsSL https://raw.githubusercontent.com/AlDanial/cloc/v2.06/cloc -o /tmp/cloc-2.06
python3 - <<'PY'
import csv
from pathlib import Path
rows = csv.DictReader(Path('reviews/bob/flow-loc-2026-11-02.csv').open())
Path('/tmp/bob-production-files.txt').write_text(
    '\n'.join(row['path'] for row in rows if row['scope'] == 'production') + '\n'
)
PY
perl /tmp/cloc-2.06 --skip-uniqueness --by-file --json --list-file=/tmp/bob-production-files.txt
```

The downloaded cloc script's SHA-256 is `ed9fbdd081a2ceb933ea490b3c1cfacc87d3898ae2650d0d6756439695a836c8`. `--skip-uniqueness` keeps distinct files in the count even when their contents match.
